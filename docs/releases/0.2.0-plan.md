## Scope

Opening work is version metadata and release documentation only. No v0.2 product feature is approved or selected at opening. [UNRELEASED](UNRELEASED.md) is the inventory for later features; record commit, behavior, migrations, configuration names, entitlements, readiness and rollout requirements for each change.

Use mobile-first Neat UI patterns and [UI guidelines](../UI-UX-GUIDELINES.md). Normal feature/fix work is TST-only and stops after tests, commit, push and documentation. This opening does not authorize another main push, production migration, tag, provider activation, or production feature change.

## Environment and release gates

The owner authorized an in-app Support feature for this development cycle on 2026-10-08, with completion resumed after a computer crash on 2026-10-09. Scope is simple reporting, organization visibility, a separate platform support queue, public responses and estimated fix dates, and reporter acknowledgement on returning to Neat. See [manifest](UNRELEASED.md), [guide](../SUPPORT.md) and [validation](0.2.0-support-validation.md) for the support migration, privacy boundaries and delivery evidence.

Keep neat-tst/tst, APP_ENV=test, DATABASE_ENVIRONMENT=test, DATABASE_TARGET_ID=neon-neat-tst and https://neat-tst.vercel.app. Verify the actual database host before any database operation; preserve existing side-effect controls. No new migration, backfill, environment variable, feature flag, dependency or external-service configuration is introduced by opening this cycle.

Before a future v0.2 release: fetch both repositories, compare actual endpoint trees and manifest, select the stable candidate, remove -dev, and complete the [pending checklist](0.2.0-checklist.md) with fresh evidence in [validation](0.2.0-validation.md). Never substitute 0.14 checks for v0.2 candidate checks. Promote only the exact tested release scope after a distinct production release request; verify deployment, environment, database, routes and tag before archiving.

## Rollback

Opening metadata/docs can be reverted without database action. Later features must document backward compatibility and any independent data recovery needs. Candidate SHA, final feature scope, release date, production deployment and release-specific rollback remain unselected.
