## Access and review preparation

**Meta:** In the developer app, configure Facebook Login and the Instagram/Facebook use cases, exact valid OAuth redirect, app domains, privacy-policy and data-deletion URLs. An app administrator must inspect each requested permission's access level in App Review and assign the legitimate human/Page/Instagram app roles for internal testing. Complete Page Publishing Authorization if the actual Page requires it. Determine whether the owned-account internal use qualifies for Standard access; broader use requires the appropriate Advanced access/review and any requested business verification. Do not label dashboard permission toggles as completed review. Direct Meta content/audio documentation returned access/rate-limit errors to the research tool, so specific optional features remain pending authoritative confirmation rather than being marked unsupported.

**Google:** [Business Profile prerequisites](https://developers.google.com/my-business/content/prereqs) require access approval for the particular Cloud project before enabling the relevant APIs. Apply with its project number through the GBP API contact form, using an actual owner/manager account and a verified active profile meeting Google's eligibility requirements. Inspect project quotas to distinguish pending from approved access. Configure a dedicated web OAuth client and consent screen/test users; enable Account Management, Business Information and the API serving Local Posts after approval. A working Gmail or Calendar grant does not establish this project access. Owner verification is a successful read-only account/location discovery in Neat, followed later by an exact approved post test.

**LinkedIn:** The [Community Management review](https://learn.microsoft.com/en-us/linkedin/marketing/community-management-app-review) requires a registered organization, verified business email, legal/business identity, website and privacy policy, and Page-super-admin application verification. Request Community Management Development access in Developer Portal Products. Standard review requires the integrated use-case demonstration and reviewer access; record omitted out-of-scope comment/inbox features explicitly in the screencast. Show OAuth, correct company Page, reviewed publishing, result readback and data handling. Record approval evidence separately for Development and Standard. The [access-tier guide](https://learn.microsoft.com/en-us/linkedin/marketing/increasing-access) distinguishes restricted, time-bounded Development testing from separately requested Standard production access; a Development post is not permanent production permission.

Discovery uses [organization ACLs](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/organizations/organization-access-control-by-role?view=li-lms-2026-09) and [organization lookup](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/organizations/organization-lookup-api?view=li-lms-2026-09). The adapter accepts only `urn:li:organization:` authors and approved Administrator/Content Administrator roles. The owner selects Echo Spirits Distilling Co.'s actual company Page after discovery; no extra brand Pages or personal profiles are created.

## Delivery guarantees and boundaries

Provider adapters never schedule a second native copy; Neat owns scheduling. Each irreversible request first persists `publicationStarted` and then invokes the current server authorization/approval/live-switch guard. Container/media IDs are checkpointed as soon as returned. Transport interruption or a publish-side server error is ambiguous; recovery checks the existing identifier or asks for review instead of blindly sending again. Explicit rate-limit rejection can use bounded retry. There is no universal exactly-once claim.

Graph HTTP 4xx rate-limit bodies are classified independently of HTTP 429: plain codes 4/17/341 follow the [maintained official Business SDK](https://raw.githubusercontent.com/meta/facebook-php-business-sdk/main/src/FacebookAds/Http/Exception/RequestException.php), and 32/613 follow Meta's [official PHP Graph SDK](https://raw.githubusercontent.com/facebook/facebook-php-sdk-v4/5.x/src/Facebook/Exceptions/FacebookResponseException.php) (older primary source). Permissions 10/200–299 and token 190 require authorization repair. Direct current rate-limit/error-guide fetching was blocked/rate-limited; no live failure was induced. Unknown subcodes are not promoted to automatic throttle retries. Public-write 5xx, API service codes 1/2, or other explicitly transient bodies remain ambiguous and require reconciliation; provider bodies/secrets are excluded from diagnostics.

An explicit native-finishing instruction records a **manual** delivery. That path allows copy, links and native finishing requirements without falsely requiring the plain-Story API's Business-only eligibility or caption restrictions. Immutable media metadata, common preparation bounds, company-Page scope and Google's policy acknowledgement still apply. Unknown structured options remain rejected; describe the requested native steps in the reviewed instructions. The provider public-request guard also refuses a manual revision even if invoked directly. Completion requires a separate administrator-recorded result; it is never an automatic API success.

Public cancellation/deletion is deliberately absent: canceling a Neat job prevents unsent work; already-started work requires outcome reconciliation. No API request to alter existing social content is authorized by implementation. Interrupted LinkedIn video or Facebook Reel uploads retain their remote ID and require review before a replacement attempt; they do not silently create a public replacement.
