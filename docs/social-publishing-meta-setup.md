## Internal testing versus broader approval

Keep the first authorization restricted to legitimate app-role users and owned/managed accounts. Record the permissions actually granted and the dashboard's access level; a successful development login does not establish general access.

Before people without an app role or external businesses connect, inspect the [current access-level/release requirements](https://developers.facebook.com/docs/development/release/) and request the appropriate **Advanced Access/App Review per permission**, plus business verification and other dashboard requirements where shown. Prepare public policy/deletion information, reviewer access and an end-to-end permission-use demonstration. Public demonstration posts require separate explicit authorization. Do not describe an app-role test as completed broader review.

## Route compatibility gate

Neat supports the existing scope-based user-code route and an optional **verified User access token** Facebook Login for Business configuration. For the latter, set the matching numeric `SOCIAL_META_CONFIG_ID` and `SOCIAL_META_TOKEN_TYPE=USER` only after reading the actual configuration. The authorization URL uses `config_id` in place of `scope`, while retaining code grant, exact callback and independent session-bound one-use state. User-code/long-lived-user exchange and Page discovery stay the same. Unknown/system-user configurations fail closed; the operator setting is an attestation, not remote token introspection or a permission grant. Do not select a System-user configuration or Unified Login template for this implementation.

The actual app's **API setup with Facebook login** view confirms that the Page-linked route still works and is now legacy; Unified Login is the route for new features. Its **Permissions and features** view offers the exact `instagram_basic` and `instagram_content_publish` names used here. Configure individual needed permissions rather than accepting a Unified template's additional ads, messaging or comment scopes. The user-token configuration wizard skips asset selection and states that standard-access permissions are requested only from app-role users.

Meta's current [Facebook Login for Business documentation](https://developers.facebook.com/documentation/facebook-login/facebook-login-for-business#user-access-token-configurations), [manual login flow](https://developers.facebook.com/documentation/facebook-login/guides/advanced/manual-flow) and [long-lived user-token guide](https://developers.facebook.com/documentation/facebook-login/guides/access-tokens/get-long-lived) support this optional user-token route. A future system-user integration requires its own token handling, asset delegation and acceptance work.

Current Meta developer pages for app creation, roles, access levels, login and deletion returned access/rate-limit failures to the research tool. The wizard labels above come from the current owner-visible dashboard; universal internal-access exemptions could not be independently confirmed from the developer pages. The actual dashboard must resolve permission and eligibility requirements. The official Meta Postman and [maintained Meta sample](https://github.com/fbsamples/reels_publishing_apis/tree/main/insta_reels_publishing_api_sample) support the Page-linked professional-account route; their examples are not proof of this app's actual grants.
